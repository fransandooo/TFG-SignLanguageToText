\chapter{Methodology and Work Plan Overview}
\setcounter{section}{0}

This chapter presents the methodology followed throughout the project, outlining the resources and
tools employed, the technical approaches adopted at different stages, the workflow used to guide
development and the sequence of activities undertaken. It also discusses the practical and
technical constraints that influenced the decisions made during implementation. The technical
development of the system is described in Section~\ref{sec:system_design} and following, while the
experimental evidence is reported in Section~\ref{sec:exp_methodology} and following.

\section{Materials and Resources}
\label{sec:plan_materials}
% =============================================================================

The project required three resource categories: (1) Hardware; (2) Software Stack; and (3) Datasets.
Each category is described below and cross-referenced to the chapter section where the technical
detail is reported.

\subsection{Hardware}

All training, evaluation and landmark extraction were performed on a single local workstation whose
specification is the operational environment of Section~\ref{sec:operational_environment}. The full
table of components and version constraints is Table~\ref{tab:operational_environment} and is not
repeated here. The relevant hardware resource for the work plan is the GPU, an NVIDIA RTX~3050~Ti
Laptop with 4\,GB of VRAM. The practical implications of this memory ceiling are discussed in
Section~\ref{sec:plan_constraints}.

\subsection{Software Stack}

The training and evaluation pipeline runs on Python~3.10 with PyTorch~2.x and CUDA~12.x. Pose
estimation uses MediaPipe Hands~0.10+, video decoding uses OpenCV~4.8+, and version control is
provided by Git with GitHub as remote host. The mobile client is built with React Native and Expo.
The inference server uses FastAPI~0.111 with Uvicorn~0.29. Documentation is written in \LaTeX. The
exact version constraints are locked in \texttt{pyproject.toml} for the training package and in
\texttt{04\_server/requirements.txt} for the inference server, so that the operational environment
can be reconstructed from a clean clone of the repository (cross-reference:
Section~\ref{sec:operational_environment} and the reproduction guide at
\texttt{docs/reproducibility\_guide.md}).

\subsection{Datasets}

The project used six datasets, grouped by their role in the development process.

\begin{enumerate}
    \item \textbf{EgoHands.} EgoHands provides annotated hand images recorded from egocentric video.
          It was used during the initial hand-localisation stage to train and evaluate a detector
          capable of finding hands before any sign-recognition model was applied.
    \item \textbf{Kaggle Hand Dataset.} The Kaggle Hand Dataset supplied additional hand images for
          the same localisation stage. It increased the visual variability of the detector training
          data and complemented EgoHands with examples from different capture conditions.
    \item \textbf{Sign Language MNIST.} Sign Language MNIST contains static greyscale images of
          alphabet handshapes. It was used only in the exploratory letter-classification stage,
          where the objective was to test whether a simple image classifier could recognise isolated
          hand configurations.
    \item \textbf{ASL Alphabet.} The ASL Alphabet dataset contains static colour images of
          American Sign Language (ASL) alphabet signs. It supported the same early
          letter-recognition branch as Sign Language MNIST, but it did not form part of the final
          word-level recognition pipeline because it does not contain temporal sign videos.
    \item \textbf{WLASL.} The Word-Level American Sign Language (WLASL) dataset is the main video
          benchmark used for word-level ASL recognition. The project builds WLASL30 for controlled
          architecture comparison and also uses larger WLASL subsets to analyse vocabulary scaling.
    \item \textbf{MS-ASL.} The Microsoft American Sign Language (MS-ASL) dataset is an independent
          word-level ASL video dataset reconstructed from public video sources. The project uses
          MS-ASL50 as a cross-dataset validation benchmark to test whether the selected recognition
          pipeline generalises beyond WLASL.
\end{enumerate}

\section{Methods}
\label{sec:plan_methods}
% =============================================================================

This section describes the methods used to carry out the work introduced in Chapter~1. It covers
the theoretical basis, algorithms, metrics, exploratory case studies and replication support used
in the project. Exact hardware specifications are reported in
Section~\ref{sec:operational_environment}; exact experimental hyperparameters are reported in
Section~\ref{sec:exp_methodology}.

\subsection{Theoretical and Algorithmic Basis}

The final recognition method is based on supervised sequence classification. Each input sample is a
short ASL video clip, and the output is a gloss label from a fixed vocabulary. The method combines
pose estimation, recurrent sequence modelling and temporal attention.

Pose estimation provides the input representation. A landmark is a three-dimensional keypoint that
represents a specific position on the detected hand, such as a fingertip or joint. MediaPipe Hands
estimates 21 landmarks per detected hand, so each valid frame is represented as 63 scalar features.
This converts the recognition problem from pixel-based video classification into classification
over structured skeletal sequences.

The sequence model uses Gated Recurrent Unit (GRU) layers for temporal modelling. A bidirectional
GRU (BiGRU) layer processes the landmark sequence in forward and reverse temporal order, then
combines both hidden-state streams. Training recurrent layers uses Backpropagation Through Time
(BPTT), which unfolds the sequence across time steps so that the loss can update the recurrent
weights. The selected architecture adds a temporal attention layer over the BiGRU outputs and uses
the resulting context vector for classification. Throughout the document, this full architecture is
referred to as the GRU+Attention model.

\subsection{Recognition Pipeline}
\label{subsec:recognition_pipeline}

The implemented recognition pipeline has four stages:

\begin{enumerate}
    \item \textbf{Video acquisition and decoding.} The input is a labelled video clip from WLASL,
          MS-ASL or the runtime prototype. OpenCV decodes the clip frame by frame. The output is an
          ordered frame sequence that preserves the temporal structure of the sign.
    \item \textbf{Landmark extraction and normalisation.} MediaPipe Hands estimates 21
          three-dimensional landmarks per frame. The coordinates are wrist-centred and
          length-normalised by the wrist-to-middle-finger distance. Frames where MediaPipe fails are
          linearly interpolated from neighbouring valid frames, and clips with a detection rate
          below 0.3 are discarded. The output is a per-clip \texttt{.npy} array of shape
          $(T, 21, 3)$ plus metadata.
    \item \textbf{Training-time augmentation.} During training, the landmark coordinates are
          transformed through rotation, scaling, translation, additive Gaussian noise and horizontal
          mirroring. These operations simulate variation in signer position and execution while
          preserving the skeletal representation.
    \item \textbf{Sequence classification.} The GRU+Attention architecture receives the landmark
          sequence and produces class scores over the selected gloss vocabulary. The same training
          loop also supports the alternative architectures compared in
          Section~\ref{sec:exp_phase2}, so the comparison changes the sequence-modelling component
          while keeping the input representation fixed.
\end{enumerate}

\subsection{Training, Metrics and Validation}

Training uses AdamW optimisation, cross-entropy loss with label smoothing, cosine learning-rate
annealing and early stopping. The numerical values of these hyperparameters are reported in the
experimental setup of Section~\ref{sec:exp_methodology}.

The evaluation metrics are Top-1 accuracy, Top-5 accuracy, Macro-F1 and balanced accuracy. Top-1
accuracy measures whether the highest-scoring prediction matches the ground truth. Top-5 accuracy
measures whether the ground truth appears within the five highest-scoring predictions. Macro-F1
averages per-class F1 scores without weighting by class frequency, while balanced accuracy averages
per-class recall.

Validation uses Stratified 5-Fold Cross-Validation, multi-seed evaluation, sequence-length analysis
and cross-dataset validation. Stratified 5-Fold Cross-Validation preserves the per-class
distribution across folds. Multi-seed evaluation repeats the same configuration under different
random seeds and reports mean and standard deviation. Sequence-length analysis tests the effect of
the temporal input window. Cross-dataset validation retrains the same pipeline on MS-ASL50 to
assess generalisation beyond WLASL.

\subsection{Exploratory Case Studies}

Two exploratory case studies preceded the final landmark-based method. The first used You Only Look
Once version 8 nano (YOLOv8n) for hand localisation on EgoHands and the Kaggle Hand Dataset. The
second used Convolutional Neural Network (CNN) classifiers for static ASL letter recognition on
Sign Language MNIST and ASL Alphabet. These studies showed that hand localisation and isolated
letter classification were tractable, but they did not address the temporal structure required for
word-level ASL recognition. Their role in the final method is therefore diagnostic: they justify
the shift from pixel-based letter recognition to landmark-based word recognition.

\subsection{Proof-of-Concept Design and Expected Outcomes}

The proof of concept connects the trained recognition model to a runtime application. The mobile
client captures a short video clip and sends it to a FastAPI server. The server applies the same
MediaPipe landmark extraction used during training, loads the selected checkpoint and returns
Top-$K$ predictions with confidence scores. The client can display the prediction shortlist and
optionally convert the Top-1 label to speech.

The expected outcome of the proof of concept is not a deployment-ready translator. Its purpose is
to demonstrate that the trained landmark-based recogniser can be integrated into an end-to-end
capture, inference and response loop. The quantitative validity of the recognition model is
therefore assessed in the Experiments chapter, while the prototype demonstrates the feasibility of
using the selected model in an interactive setting.

\subsection{Replication Support}

Replication depends on controlled configuration and traceable experiment outputs. Dataset paths,
model options and training settings are stored in YAML configuration files under \texttt{configs/}.
Each training or evaluation run writes an \texttt{experiment\_manifest.json} file with the git
commit, resolved configuration, hardware identifier, wall-clock time and final metrics. The
development environment is specified through \texttt{pyproject.toml} for the training package and
\texttt{04\_server/requirements.txt} for the inference server. The full reproduction procedure is
documented in \texttt{docs/reproducibility\_guide.md}.

\section{Methodology}
\label{sec:plan_methodology}
% =============================================================================

The project followed a Lean Startup-inspired iterative methodology. In this work, the term does not
refer to commercial product validation. It refers to short research and development cycles in which
a technical assumption is built, measured and revised before the next cycle begins. This approach
was appropriate because the early project direction changed after the exploratory stage, and the
work plan had to preserve room for evidence-driven correction.

Each iteration followed four stages:

\begin{enumerate}
    \item \textbf{Hypothesis definition.} The input was a previous devlog entry, tutor comment,
          experimental result or implementation problem. The output was a testable technical
          hypothesis, together with the dataset, metric and configuration needed to evaluate it.
    \item \textbf{Build.} The input was the hypothesis and the current repository state. The output
          was an implementation change, a YAML configuration file or both, committed to Git so that
          the experiment could be traced to a specific version of the code.
    \item \textbf{Measure.} The input was the committed implementation and its configuration. The
          output was a set of experiment artefacts: metrics, checkpoints, plots and an
          \texttt{experiment\_manifest.json} file.
    \item \textbf{Learn.} The input was the measured evidence from the previous stage. The output
          was a documented decision to keep, revise or discard the hypothesis, recorded in the
          development log before the next iteration began.
\end{enumerate}

The pivot recorded in Section~\ref{sec:exp_phase1} is the clearest application of this loop. The
project began with a pixel-based route that combined hand localisation with static letter
classification. The detector and the letter classifiers were functional on their own datasets, but
the combined route showed that the central problem was not locating the hand. The central problem
was representing the temporal structure of complete signs. The next iteration therefore replaced
the pixel-based recognition route with the landmark-based word-recognition pipeline used in the
rest of the project.

Tutor meetings acted as external review checkpoints within the iterative process. Examples include
removing Test-Time Augmentation (TTA) from the final evaluation protocol, adopting Stratified
5-Fold Cross-Validation, extending validation to MS-ASL50 and adding multi-seed evaluation to
reduce dependence on a single random initialisation.

Documentation was maintained as part of the methodology rather than as a final clean-up task. A
structured development log was kept throughout the project, containing dated entries for each main
work session and recording the hypothesis, change, result and next action of each iteration. The
work plan in Section~\ref{sec:plan_workplan} is reconstructed from that log, the proposal,
experiment artefacts and supervision notes.

\section{Work Plan}
\label{sec:plan_workplan}
% =============================================================================

The executed work plan was reconstructed from the original proposal, development notes, experiment
artefacts and supervision notes. It is organised into seven phases (A--G): the first two correspond
closely to the proposal-era plan, while the remaining phases reflect the methodological pivot from
static, pixel-based recognition to landmark-based word-level ASL recognition.

The original work plan from the project proposal (January 2026) followed a sequential structure
with separate phases for hand detection, static handshape recognition, dynamic sign recognition,
temporal fusion, language generation, mobile prototype, integration and validation. The executed
plan diverged after the methodological pivot described in Section~\ref{sec:exp_phase1}, which
replaced the static letter recognition route with landmark-based word recognition and folded the
temporal fusion stage into the selected sequence model.

Figure~\ref{fig:work_plan_timeline} summarises the executed work plan at the start of the section.
The chart shows the start and end of each phase and makes the main deviation from the initial
proposal visible: the shift from static letter recognition to landmark-based word-level
recognition.

\paragraph{Phase A: Project framing and proposal (5 January 2026 to 16 January 2026).} The project formally started with problem definition, preliminary literature review, scope
selection and proposal preparation. This phase defined the accessibility motivation, the initial
system architecture, the first work schedule and the research direction. No model training was
carried out at this stage. The main output was the approved project proposal and its initial
planning material.

\paragraph{Phase B: Hand detection and static letter recognition (12 January 2026 to 20 January 2026).}
The initial technical work explored the proposal's first recognition route: localising hands in
images and classifying static ASL letters. A YOLOv8n detector was trained on a combined EgoHands
and Kaggle Hand Dataset corpus, and CNN-based classifiers were explored on static ASL alphabet
datasets. These components reached working performance on their own tasks, but they also revealed a
limitation in the original direction: the central research challenge was not hand localisation, but
representing the temporal structure of complete signs.

\paragraph{Phase C: Landmark pivot and WLASL30 baseline (21 January 2026 to 19 February 2026).}
The project pivoted from pixel-based letter recognition to word-level recognition using MediaPipe
hand landmarks. WLASL30 was built as the first controlled benchmark, and several sequence
architectures were compared under the same landmark input representation. The GRU+Attention
architecture became the best-performing configuration because it combined recurrent temporal
modelling with an attention layer able to weight informative frames. After supervisory review, TTA
was excluded from the final evaluation protocol, and the WLASL30 result was strengthened through
Stratified 5-Fold Cross-Validation.

\paragraph{Phase D: Vocabulary scaling and ethical framework (19 February 2026 to 10 April 2026).}
Once the GRU+Attention model had been selected, the next phase tested how the approach behaved as
the WLASL vocabulary increased beyond the initial 30-class setting. The model was retrained on
progressively larger WLASL subsets to quantify the effect of vocabulary size and per-class data
scarcity. In parallel, the ethical and social-impact chapter was developed, including the
accessibility motivation, privacy implications of landmark-based representations, bias
considerations, reproducibility and the responsible-deployment limits of the prototype.

\paragraph{Phase E: Runtime prototype (13 April 2026 to 20 April 2026).} The technical work expanded from offline training to a runtime proof of concept. A mobile client
and FastAPI server were integrated so that short clips could be captured, sent for inference and
returned as Top-$K$ word predictions. Additional prototype features included text-to-speech, model
selection from the client and a heuristic continuous-prediction demo mode based on overlapping
windows. This phase demonstrates end-to-end feasibility, but it is not treated as the main research
result. The quantitative contribution remains the landmark-based recognition pipeline and its
validation.

\paragraph{Phase F: Refactoring and cross-dataset validation (20 April 2026 to 23 April 2026).}
The notebook-based experimental code was consolidated into a modular Python package, with
configuration-driven training, structured experiment manifests, reusable evaluation scripts and
preserved checkpoints and plots. This refactor improved reproducibility and made it possible to
rerun the same pipeline across datasets. MS-ASL50 was then added as an independent validation
benchmark, and the final evaluation protocol incorporated multi-seed runs, a sequence-length
analysis, cross-dataset validation and comparison against the WLASL results.

\paragraph{Phase G: Documentation and qualitative validation (24 April 2026 to 25 May 2026).}
The final phase focused on document writing, result consolidation, figure and table preparation and
qualitative validation of the runtime prototype. The experimental chapter was organised into
quantitative and qualitative tracks. The quantitative track reports completed model evaluations,
while the qualitative track describes the participant protocol and reports the usability evidence
collected from the participant sessions.

\section{Constraints and Limitations}
\label{sec:plan_constraints}
% =============================================================================

This section lists the constraints that shaped the work plan and implementation. They are ordered
by their impact on project scope and design. Limitations of the experimental conclusions
themselves, including standard deviations, test-set granularity and single-architecture
cross-dataset validation, are treated separately in Section~\ref{sec:exp_limitations}.

\begin{enumerate}
    \item \textbf{Computing capacity.} Every training and evaluation run executed on a single
          NVIDIA RTX~3050~Ti Laptop GPU with 4\,GB of VRAM. This imposed a hard memory ceiling on
          the temporal window, batch size and model size that could be tested. The practical effect
          was to prioritise compact recurrent architectures and to exclude larger video models that
          would not fit reliably within the available hardware.

    \item \textbf{Dataset reconstruction and landmark coverage.} Both word-recognition datasets
          depend on external video sources rather than on locally distributed video files. WLASL
          relies on URLs that have decayed since publication, and the MediaPipe detection rate on
          the surviving WLASL clips is approximately 69\,\%. MS-ASL is reconstructed from
          per-instance YouTube URLs, and the reconstruction audit records a download success rate of
          65.9\,\% (16{,}816 of 25{,}513 clips). This constrained the effective number of usable
          training examples and determined the feasible subset definitions, including the use of
          MS-ASL50 instead of the more standard MS-ASL30 baseline used in WLASL-style comparisons,
          since only six MS-ASL classes met the train/val/test sample threshold needed for an
          MS-ASL30 reproduction (cf.\ Section~\ref{sec:exp_msasl}).

    \item \textbf{Experimental calendar.} The executed work plan ran from 5 January 2026 to the
          final submission window in May 2026. This fixed calendar limited how many repeated
          experiments could be completed. Multi-seed evaluation was applied to the main reported
          configurations, but broader vocabulary-scaling runs and additional cross-dataset
          architecture comparisons were not included in the experimental scope.

    \item \textbf{Linguistic scope.} The project validates a single sign language, American Sign
          Language, and uses ASL exclusively for both the WLASL and MS-ASL benchmarks. The pipeline
          contains no ASL-specific rule-based component, and each component that consumes landmarks
          could in principle be retrained on a different sign language given a comparable dataset.
          That validation has not been performed, so transfer to Spanish Sign Language, British
          Sign Language or any other sign language remains future work.
\end{enumerate}
